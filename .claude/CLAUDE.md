## Architecture

A daily AWS data pipeline that tracks departure delays at San Diego (KSAN):

1. **Ingest — Lambda** (`main/api_handler.py` + `main/flight_aware_api.py`). Gets yesterday's departures from the FlightAware AeroAPI and writes them gzipped as JSON Lines to `s3://$RAW_BUCKET/raw/flightaware/airport=KSAN/departures_<YYYY-MM-DD>.jsonl.gz`, adding an `_ingested_at` field to each row. "Yesterday" means the America/Los_Angeles calendar day, converted to a UTC window. The event can override it with `start`/`end`. The date in the S3 key comes from slicing the `start` timestamp. Env vars: `RAW_BUCKET`, `FLIGHT_API_KEY`. The API client is limited by design: at most 5 pages, a 62s sleep between pages to stay under the rate limit, and it raises if a flight's `actual_off` is outside the window or if no flights come back.
2. **Transform — Glue (PySpark)** (`main/transformations.py`). Reads the raw JSONL with the fixed `RAW_SCHEMA`. It gets `dt` from the filename, not from the data. `clean_flights` chains small pure functions: `parse_timestamps` → `dedupe_flights` (on `(dt, fa_flight_id)`, keeping the latest `_ingested_at`, dropping null ids) → `drop_missing_departure` (drops rows with null `departure_delay`) → `split_ident` (`ident_icao` → `airline_code`/`flight_number`) → `add_runway_delay` (`runway_delay` = actual_off − actual_out in seconds, negative → null) → `pst_time`. Output columns: `dt, fa_flight_id, airline_code, flight_number, code_icao, scheduled_out, scheduled_off, actual_out, actual_off, departure_delay, runway_delay` (delays are int seconds; timestamps are converted to LA time by `pst_time`). `log_dropped_flights` prints how many rows dedupe and the null-departure filter dropped; it is a separate function so the counts can be tested. Before writing, `date_types` casts `dt` to `date` and the timestamps to `timestamp_ntz` to match the Iceberg schema. The write goes through the `IcebergTable` class (database `flights`, table `silver_flights`, warehouse `s3://$CLEAN_BUCKET/iceberg/`): `spark_settings()` returns the Iceberg/Glue-catalog Spark config as a dict (applied via `SparkConf` before the `SparkContext` is created, and testable without Spark), `full_name` is `glue_catalog.flights.silver_flights`, and `overwrite_days` calls `writeTo(...).overwritePartitions()`, so reruns and backfills replace only the days being written. The job raises if no clean rows are produced. Glue args: `RAW_BUCKET`, `CLEAN_BUCKET`, and optionally `START_DATE`/`END_DATE` for backfills (the default is yesterday in UTC). `awsglue` is imported only inside `main()`, so the pure transform functions can be unit tested with plain PySpark.
3. **Serve — Athena views** (`main/sql/`). These build on `flights.silver_flights`. Its DDL is in `main/sql/ddl/silver_flights.sql`: an Iceberg table (Parquet, zstd) at `s3://brendan-silver-flights/iceberg/silver_flights/`, using hidden partitioning `PARTITIONED BY (day(dt))`, so no crawler, `MSCK REPAIR`, or year/month/day columns are needed. CD does **not** run the DDL; apply it by hand if it changes (and keep `RAW_SCHEMA`/`clean_flights`/`date_types` in step with it). `core/` holds the base views (`00_airlines` lookup, then `01_airlines_tracked`, which joins silver to airlines and adds `total_delay_secs`). `web/` (`10_`–`17_`) holds the `web_*` views that feed the website (top delays, avg delay per airline, % delayed, total delay, each with a `_yesterday` and a `_month` version; the total-delay views split the sum into `days_wasted`/`hours_wasted`/`minutes_wasted`/`secs_wasted`). CD runs the files in glob/filename order, `core/*` before `web/*`, so the numeric prefixes set the dependency order. Number new files to match. Each file must be a single `CREATE OR REPLACE VIEW` statement. The "total delay" rule is defined once in `airlines_tracked` as `total_delay_secs = gate_delay + takeoff_delay`: `gate_delay` is `departure_delay` minus a 600s (10 min) grace period, floored at 0; `takeoff_delay` is 0 if wheels-up was within 1200s (20 min) of `scheduled_off`, otherwise `runway_delay − 1200` (floored at 0), or, when `runway_delay` is null, `(actual_off − scheduled_off) − departure_delay − 1200` floored at 0. Web views filter directly on `dt` (Iceberg's `day(dt)` partitioning prunes on it), and views that output `dt` must `CAST(dt AS VARCHAR)` because the exporter doesn't support `date`. The `_yesterday` views use yesterday's LA date (`date(current_timestamp AT TIME ZONE 'America/Los_Angeles') - interval '1' day`), since data lands the next morning. Running them between midnight and when the pipeline finishes returns empty results.
4. **Export — Lambda** (`main/export_handler.py` + `main/athena_exporter.py`). `AthenaExporter` is a class that wraps a boto3 Athena client (workgroup `flight-aggregations`, database `flights`). It starts every query first, then polls each one with a timeout (`wait_for_query`), then pages through the results (`get_rows`), converting Athena types to Python types. Only `varchar`/`integer`/`bigint`/`double`/`boolean` are supported; any other type raises `ValueError`, so new view columns must use one of those. `fetch_views` returns `{view name without "web_": rows}`. The handler runs every view in `VIEWS` and writes one JSON document `{data_date, views, generated_at}` to `s3://$WEB_BUCKET/data/web/airport=KSAN/<YYYY-MM-DD>.json`, where the date is yesterday in LA. Env var: `WEB_BUCKET`. A new web view must also be added to `VIEWS`. After the JSON, the handler renders the website with `pages.SITE.render_all(document)` and writes each page to `s3://$WEB_BUCKET/<page key>` (e.g. `index.html`) with `ContentType: text/html; charset=utf-8` and `CacheControl: max-age=300`. It uses only boto3 and the standard library, which the Lambda runtime provides.
5. **Website — HTML rendering** (`main/page_base.py` + `main/pages.py`, static assets in `website/`). Pages are built in Python with `string.Template` and `html.escape` (no templating library, so nothing extra goes in the Lambda zip). `page_base.py` holds the generic pieces: `LAYOUT` (shared HTML shell that links `style.css`, a nav bar, a "Data for <data_date>" footnote, and optional `<script>` tags), `Page` (`key` = output filename, `title`, `nav_label`, `content`, `scripts`; `nav_html` marks the current page's link `class="active"`; `render(document, site_pages)` fills `LAYOUT` with `content.body(document)`), and `Site` (takes a list of content objects, calls each one's `page_params()` to get its `Page`, raises `ValueError` on duplicate keys, and `render_all(document)` returns `{page key: html}`). `pages.py` holds the site-specific content. Each page is a content class with two methods: `page_params()` returns its `Page` (passing `content=self`), and `body(document)` returns the inner HTML. `HomePage` (`index.html`, loads `counter.js`) shows two `DelayCounter`s built from the `total_delay_yesterday` and `total_delay_month` rows. `missing_check(views, name)` returns the first row of a view, or `{}` if it's empty, so missing data/NULLs show as 0. `DelayCounter` renders the days:hours:min:sec blocks and puts `total_seconds` in `data-total`, which `website/counter.js` (`CountUpCounter` class) animates up from 0 (skipped when the user prefers reduced motion). `pages.SITE` is the module-level `Site` the handler uses, so to add a page write a new content class in `pages.py` and add it to `SITE`. `website/preview.py` renders the site locally from a sample document into `website/` (open `website/index.html` in a browser); `style.css` is the shared dark-theme stylesheet. Tests are split to match the modules: `test_files/test_page_base.py` covers `Page`/`Site`, and `test_files/test_pages.py` covers `missing_check`, `DelayCounter` and `HomePage`.

## CI/CD and branching

- Work lands on `development` and is merged to `main` by PR.
- **CI** (`.github/workflows/ci.yml`) runs `pytest` on Python 3.11 for pushes to `development` and for PRs into `development`/`main`.
- **CD** (`.github/workflows/cd.yml`) runs on every push to `main` (or manually through `workflow_dispatch`), on Python 3.14. It builds two zips, and each one includes only the files named in its build step, so any new module or dependency must be added there:
  - `api_function.zip`: `api_handler.py` + `flight_aware_api.py` + `requests` → ingestion Lambda (`LAMBDA_INGES_NAME`).
  - `export_function.zip`: `export_handler.py` + `athena_exporter.py` + `pages.py` + `page_base.py` → export Lambda (`LAMBDA_EXP_NAME`). `export_handler.py` imports `pages`, which imports `page_base`, so all four files must be in the zip or the Lambda fails on import.
  - Nothing deploys `website/style.css` or `website/counter.js` yet; they must be uploaded to the root of `$WEB_BUCKET` (next to `index.html`) for the pages to be styled and animated.
  
  In order, it deploys the ingestion Lambda, copies `transformations.py` to the Glue job's existing script S3 location, runs `core/*.sql` then `web/*.sql` through the Athena workgroup `flight-aggregations` (it stops on the first failed query), and finally deploys the export Lambda. AWS settings come from repo variables (`AWS_ROLE_ARN`, `AWS_REGION`, `LAMBDA_INGES_NAME`, `LAMBDA_EXP_NAME`, `GLUE_JOB_NAME`) using OIDC.
